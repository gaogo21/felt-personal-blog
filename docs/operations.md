# 运行、备份与恢复

## 环境与持久化

配置通过环境变量注入；不要提交真实 `.env`、数据库密码、管理员密码、备份密钥、Cookie 密钥或私有媒体。`Blog__StoragePath` 必须是绝对路径，位于静态资源目录之外且祖先目录不能是符号链接。Unix 下私有目录使用 0700、上传与备份文件使用 0600。

数据库和媒体目录必须一起保留。Cookie/Data Protection 密钥在私有目录 `keys/`，丢失会使已有登录失效，但不会删除博客内容。普通启动检查迁移和站点初始化是否完成；先运行 `--migrate`，首次创建管理员再运行 `--init-admin`。管理员密码通过 `Blog__AdminPassword` 注入，不能少于 12 个字符。`--reset-admin` 更新密码并作废旧会话。

本机 `eng/dev.sh` 自动加载已忽略的 `runtime/dev.env`；设置 `FELT_ENV_FILE` 可选择其他环境文件，设为空字符串可完全使用当前进程环境。不要加载不可信的 shell 环境文件。

## 生产服务

使用 Production 环境、实际 `AllowedHosts`、随机数据库密码和独立的 `Backup__Key`。生成密钥可以运行 `openssl rand -base64 32`；妥善保存输出到密码管理器或部署 secret。密钥不能和唯一一份备份保存在同一个位置。

生产管理路径和管理 API 要求 HTTPS。将应用放在 HTTPS 反向代理后，传递原始 Host、`X-Forwarded-Proto` 和 `X-Forwarded-For`；`ReverseProxy__KnownProxy` 设置为应用实际看到的代理 IP，仅信任该代理（框架默认还信任本机回环）。不要信任所有转发来源。应用监听端口只对本机/代理开放，数据库不向公网开放。跨域写入会被拒绝；反向代理请求体限制应至少允许 210 MiB 的 multipart 上传。

容器运行用户为 `app`。命名卷默认负责持久化和目录所有权；若使用宿主机 bind mount，应预先给容器运行用户正确权限。开发配置只供本机 HTTP 验证，不能作为生产部署配置直接公开。

ClamAV 官方签名需定期由运维更新；容器首次没有签名时尝试下载。签名缺失或工具失败时，媒体保持隔离并重试，最多三次后显示拒绝原因；恢复工具后可从媒体库手动重试。不会把扫描失败的文件标为就绪。FFmpeg/FFprobe 的可执行路径来自部署配置，用户输入不能指定工具路径或参数。

健康检查 `/health/live` 检查进程；`/health/ready` 检查数据库、迁移和存储目录。它不代表 ClamAV 签名新鲜度；运维仍需检查工具和签名更新。

## 内容和媒体备份

管理后台“备份与操作记录”要求再次验证密码，创建包含内容实体、草稿、发布版本、引用关系、站点配置以及上传原件/就绪文件的备份。写入期间与内容服务共享数据库锁；正在执行的媒体工具可以继续计算，但提交必须等待备份结束。

备份位于私有 `backups/<UUID>.felt`。格式为版本 1 的逻辑 ZIP，外层使用 32 字节密钥和 AES-256-GCM 的 64 KiB 分块认证，含必需的终止记录。篡改、顺序变化、截断和额外字节会被拒绝。解密后还会核对 ZIP 路径、数量、每个媒体大小与 SHA-256；恢复内置素材时核对当前发布包里的素材哈希。上传文件总量上限 10 GiB；创建和恢复需要额外临时磁盘空间，文件数据流式处理。

备份不包含管理员、密码哈希、会话、Cookie 密钥和幂等请求凭据。应用自带的 `dist/assets` 不复制进备份，需要保留匹配的应用版本。备份也不是 PostgreSQL WAL 或完整机器快照；数据库基础设施备份由运维另行管理。

Development 没有提供 `Backup__Key` 时会生成仅本机的 `private/backup.key`。该文件丢失则无法解密对应备份。Production 不生成默认密钥，缺少密钥时拒绝创建备份。密钥更换后旧备份仍需旧密钥；保留历史密钥与备份的对应关系。

将 `.felt` 文件复制到独立存储，并定期做恢复演练；不要只依赖与媒体同盘的一份备份。

## 独立恢复演练

1. 保留源库与源媒体不动，准备同一应用版本和正确备份密钥。
2. 显式创建全新数据库，名字必须为 `felt_restore_` 开头；目标 public schema 不能已有表。准备与源存储不重叠的空私有目录。
3. 在配置仍指向源库/源存储的环境中执行下面的命令。恢复命令只向 `--target` 指定的新库及 `--restore-storage` 指定的新目录写入。

```sh
dotnet run --project src/Blog.Web -- \
  --restore /绝对路径/备份UUID.felt \
  --target 'Host=数据库地址;Database=felt_restore_20261012;Username=恢复用户;Password=恢复密码' \
  --restore-storage /绝对路径/独立恢复目录
```

目标库不能与源库同名，也不能在非空库上覆盖恢复。目标迁移前检查是否已有表，校验或写入失败会清理本次恢复出的媒体文件。处理中的任务清除旧租约，恢复后的 worker 会重新获取任务；处理中输入原件也包含在备份里。

恢复成功后，另一个服务实例使用目标连接串和目标私有目录，显式 `--init-admin` 建立新管理员；确认公开页面、后台与媒体都能使用，再通过运维切换连接配置。切换前保留源环境和备份，便于回退。恢复没有自动替换源库的入口。

## 验证与故障排查

- 保存冲突：保留当前输入，重新加载最新草稿；不要直接覆盖其他窗口的修改。
- 发布失败：检查启用专栏、非空正文、正文结构、媒体就绪状态。
- 删除媒体失败：查看引用列表；历史发布版本也保留引用，清理文章会释放其草稿和历史版本引用。
- 扫描失败：检查 `clamscan`、官方签名、目录权限和管理员媒体列表中的错误码，再重试。
- 启动失败：检查数据库连接、迁移、存储绝对路径和权限。普通启动不会替你覆盖数据库或管理员。

历史数据库实体/迁移不完整，当前初始迁移仅针对新库。如以后找回旧数据库，应先导出、分析并做独立映射导入，不能直接套用当前迁移。
